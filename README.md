# Backend Development: Table Reservation API
**Course:** InfoSys 22 | **Assignment:** #1

This repository contains the backend implementation for a Table Reservation System built with Django. The primary objective of this project is to successfully translate an Entity-Relationship Diagram (ERD) into a functional database architecture and application programming interface (API) without relying on frontend technologies.

> **Note on Scope:** This project focuses entirely on backend components (`models.py`, `views.py`, `urls.py`, and `forms.py`). All frontend elements such as HTML, CSS, JavaScript, and user interfaces have been intentionally excluded from this assignment.

---

## 🏛 Architecture & Component Breakdown

Our Django application is compartmentalized into standard architectural layers. The main project settings reside in the root folder, while the core logic is handled by the `reservation_app` application.

### 1. Database Entities (Models)
The system is built upon 7 interconnected models:
- **`Customer`**: Manages user contact details.
- **`TableCategory`**: Organizes tables into specific types (e.g., VIP, Patio).
- **`Table`**: Represents physical tables. Links to a category and tracks capacity.
- **`ReservationStatus`**: A lookup table defining valid states (Pending, Confirmed, etc.).
- **`Reservation`**: The central booking entity linking a Customer, Table, and ReservationStatus.
- **`Payment`**: Financial records directly tied (1-to-1) to a Reservation.
- **`AuditLog`**: Automatically tracks history and state changes for Reservations.

### 2. Data Integrity & Validation (Forms)
Data validation is handled via Django `ModelForms`. We enforce strict business rules before any data is committed to the database:
- Guest counts must be strictly positive.
- The number of guests cannot exceed the requested table's maximum capacity.
- Reservation `end_time` must logically follow the `start_time`.
- Payments cannot have negative amounts.
*(Note: `AuditLog` does not have a form as it is generated by internal system events, not user input).*

### 3. Application Logic (Views)
Standard CRUD operations (Create, Read, Update, Delete) are implemented using function-based views. Key business logic features include:
- **Soft Deletion for Reservations**: Canceling a reservation updates its status to `CANCELLED` rather than destroying the database record.
- **Automated Audit Trailing**: Any creation, modification, or cancellation of a reservation triggers an automatic `AuditLog` entry.
- **Dynamic Filtering**: 
  - Reservations can be filtered by `?customer=<id>` and `?reservation_date=<date>`.
  - Audit Logs and Payments can be filtered by `?reservation=<id>`.
- **Pre-write Validation**: All invalid requests (time conflicts, over-capacity) are blocked prior to database interaction.

### 4. Endpoints (URLs)
All routes are namespaced under `reservation_app` to ensure modularity.
- The application utilizes path converters (`<int:pk>`) for specific resources.
- Expected routes follow a standard pattern: `/entity/`, `/entity/create/`, `/entity/<id>/`, `/entity/<id>/update/`, `/entity/<id>/delete/`.
- Status updates use specific action paths (e.g., `/reservations/<id>/cancel/`).

## 🚀 Environment Setup & Execution

Follow these steps to launch the system locally.

**1. Initialize Virtual Environment**
```bash
python -m venv venv
# For Windows:
venv\Scripts\activate
# For macOS/Linux:
source venv/bin/activate
```

**2. Install Dependencies**
```bash
pip install django
```

**3. Database Initialization**
Generate and execute the required migrations:
```bash
python manage.py makemigrations
python manage.py migrate
```

**4. Create Administrator Account**
```bash
python manage.py createsuperuser
```

**5. Launch Server**
```bash
python manage.py runserver
```
